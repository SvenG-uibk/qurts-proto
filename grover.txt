Qurts-core Grover example: unsound uncomputation shortcut, and a gap versus
the paper's own phase(pi) idiom
================================================================================

1. What was wrong

Uncompute.hs's automatic drop-reversal used to special-case "diagonal" gates
(Z, S, T, ...): when reversing a value's construction history, it skipped
re-applying a diagonal gate, on the reasoning that "a diagonal gate never
moves a qubit to a different basis branch, only phases it, so undoing it is
never necessary to reach |0>". That's true only when the diagonal gate is
applied to a qubit that's already confined to a single computational-basis
ket at the point it's applied (e.g. Grover's own phase-kickback, where the
"marked" qubit already deterministically encodes f(x)).

It is not true in general. Counterexample: apply H then Z (both bare EU,
i.e. general unitaries) to a qubit *inside one branch of a qif*, leave the
other branch untouched, and drop the qif's result. This type-checks (see
"the qif issue" below), and with the old skip logic the two branches
disagreed on the qubit's final value after the reversal -- i.e. it was left
entangled with the qif's control instead of being disentangled to |0>. That
is exactly the invalid discard Definition 2.1 forbids.

Fix applied: removed the skip entirely. Uncompute.hs now reverses every gate
via its own exact inverse, in exact reverse order, unconditionally -- which
is what the uncomputation-semantics theorem (Thm 5.4, its equivalence with
simulation semantics) actually establishes, with no gate-name-based
exception. Also closed a related gap: TypeChecker.hs's `[c](x)` (EC) rule
accepted *any* identifier as `c`, including non-classical gates like H --
`[H](x)` type-checked exactly like `[not](x)`, preserving droppability for a
gate that mixes basis states. This was only ever caught by accident,
downstream, when the gate-inverse lookup table happened not to recognise the
name. `[c]` is now restricted to names GateInverse.hs has a verified inverse
for -- not/cnot/swap plus the whole diagonal family (I/Z/S/Sdg/T/Tdg; see
point 6, below, for why the diagonal gates are included despite not being
"classical Boolean injective functions" in Section 3.2.1's literal sense).
`H` (and any other gate that actually mixes basis states) is still excluded,
since GateInverse.hs has no verified inverse recorded for it under EC at all
-- that exclusion was never really about qfree-ness, see point 6.

2. The "qif issue": why removing the skip regressed the shipped Grover example

`typ_qif`'s own rule assigns the *qif's* result type #alpha T from the
branches' type T, regardless of what tag T itself carried -- including
#bot, which can arise from a bare EU gate (e.g. H) used *inside* one branch.
We checked this against the paper's own prose (Sec 3.2.2: "the return value
of the qif statement has type #'a T ... where T is the type of the
branches") and against the paper's own toy example (`qif r { [1]() } else
{ [0]() }`, where the branches naturally produce #top, not #alpha) -- this
retagging is correct and matches the paper; it isn't the bug. The bug was
entirely in the uncomputation pass assuming it could skip a step without
checking it was safe to. With the skip removed, this exact retagging case
(H;Z inside a branch, dropped) was re-verified to uncompute correctly.

What *did* regress is the example itself: `example_grover.qurts-core`'s
oracle computed a temporary boolean-like ancilla via `oracle(x,y,z)`
(purely classical, `[not]`/qif, no phase anywhere in its own history), then
applied the phase via `let tmp = phase(tmp)` where `phase(a) = [Z](a)` --
i.e. a *rebind*. That rebind put Z into tmp's own tracked reversible
history. Once Z is no longer skipped, dropping tmp faithfully reverses Z
right next to itself (Z.Z = I), erasing exactly the phase kickback the
oracle was meant to imprint on x,y,z. Verified: post-fix, the shipped
Grover's simulated output distribution went from a clean peak at |111>
to uniform over all 8 outcomes.

This is not a bug in the fix -- it's Unqomp's own qfree criterion asserting
itself: Z is not qfree (it carries a phase, coefficient != 1), so Unqomp's
own algorithm would refuse to auto-reverse it too, and Unqomp's paper states
plainly that Grover/Deutsch-Jozsa's phase kickback is "built by hand,
entirely outside" their automatic machinery. The shipped example was
relying on an unsound shortcut to get the right numeric answer.

3. Why the paper's own phase(pi)/borrow idiom can't be transcribed into
   qurts-core as formalised

Section 3.1's own "explicit uncomputation" desugaring:

    let r = &xl;
    let tmp: #qbit = oracle(r);
    qif &tmp { phase(pi) } else { noop };
    drop tmp;

is not itself expressible in the qurts-core core calculus (Section 3.2)
this implementation follows -- confirmed directly, not assumed:

  a) `phase(pi)` is "the map -1: C -> C" (Appendix A) -- it produces no
     qubit, so a qif branch built from it has type (). `typ_qif` requires
     both branches to be Purely Quantum (Fig. 7); () fails that
     unconditionally. Verified: type-checking a `qif` with a ()-typed
     branch gives `NotPurelyQuantum "... return type is not PQ: TyUnit"`.

  b) The `qif ...;` line above is used as a bare statement -- its result is
     never named. The core grammar's `Stmt` has no "expression as its own
     statement" production; every expression must be `let`-bound.

Both are core-calculus rules, not implementation gaps specific to this
Haskell codebase. This matches the paper's own footnote 4: Grover's code
(Fig. 2, Appendix A) "use[s] some standard features from Rust... not
formally defined in Section 3.2... part of an implementation of Qurts in
development." So no encoding of Grover into qurts-core-as-specified can be a
literal transcription of Section 3.1's snippet; it was always necessarily a
translation.

4. What we did about it

Two alternative, verified-sound re-encodings of Grover's oracle and
diffusion phase step, avoiding the rebind-into-Z pattern entirely:

  - example_grover.qurts-core: direct phase oracle. Z applied straight to
    one search-register qubit, controlled by the other two via nested qif
    -- no ancilla at all, nothing ever dropped through a Z-touched value.
    Simulated: 952/1000 on |111>. Simpler circuit than the original (3
    qubits instead of 7).

  - example_grover2.qurts-core: phase-kickback ancilla. A dedicated qubit
    prepared in |-> (via [1](); H -- necessarily via bare EU, which
    permanently forfeits its droppability, matching how this type system
    already treats any general unitary). The oracle's classical
    computation is XORed into it (matching the standard textbook Grover
    ancilla trick: |-> is a -1-eigenstate of the flip, so the ancilla's own
    state is unchanged by this and never needs uncomputing at all). The
    ancilla is threaded through both Grover iterations and consumed via
    meas() at the very end (never via drop -- consistent with the type
    system already refusing to make #bot droppable). Simulated: 938/1000
    on |111>.

Both are standard ways to implement a Grover phase oracle; neither is the
paper's own borrow-based construction, because -- per point 3 -- that
construction isn't expressible in the calculus as specified.

4b. A tempting refinement that was considered and rejected: basis-tracking

Before settling on the two re-encodings above, we considered reinstating a
*refined* version of the diagonal skip: instead of "skip any gate named
Z/S/T", track per-value whether it is provably confined to a computational
basis ket (propagate "classical" through [0]/[1]/not/cnot/swap/X/Y/Z/S/T,
break it at H/Rx/Ry), and only skip a diagonal gate's reversal when its
input is provably classical in that sense. Checked by hand against both
cases: it correctly identifies the original oracle-ancilla pattern as safe
to skip (its whole history before Z is qif/not/[0]/[1], no H anywhere) and
correctly identifies the H;Z-in-a-qif-branch counterexample as unsafe
(H breaks classicality, forcing full reversal, avoiding the earlier bug).
So this refinement is *sound*, strictly more precise than the removed
name-based check, and would let the ancilla+Z+drop pattern -- structurally
closer to the paper's own oracle/tmp separation -- type-check and work.

We didn't implement it anyway. The reason connects directly to point 5
below: Qurts's typing judgements (Fig. 4) carry exactly two pieces of
per-variable information, a type and an Aliveness (`active` or `frozen-by-
some-lifetime`) -- nothing about the qubit's quantum state. `canDrop`,
`isPurelyQuantumType`, `typ_qif` are all syntactic (which constructs were
used) or lifetime-based (is `alpha` active); none of them, nor any theorem
in the paper, ever reasons about what basis state a value is confined to.
"Classical-basis tracking," however carefully designed and however sound
its soundness argument, is a new analysis the paper's type system doesn't
have and its theorems don't cover -- the same category of problem as the
original unsound diagonal skip, just done more rigorously. Given the goal
was to implement exactly what the paper's theorems establish and nothing
more, this was set aside in favour of the two re-encodings that need no
extra analysis at all.

5. Open question for the paper's author

Is Section 3.1's phase(pi)-via-borrow idiom intended to be part of the
*formal* core calculus, or is it deliberately scoped as "full Qurts" sugar
outside Section 3.2, same as mutable references and for-loops? If the
former, it needs: (a) a qif-branch-return exemption from the Purely Quantum
requirement specifically for this construct (or a redefinition of PQ that
admits it), (b) a grammar extension for a bare/discarded qif statement (or
an explicit "let _ = ..." binding form), and (c) a compilation rule that
Circuit.hs would need: "qif ctrl { phase(pi) } else { noop }" must compile
directly to a Z gate on ctrl's own qubit, bypassing the ordinary
per-branch-value compilation path. None of that is covered by the paper's
existing theorems (4.5, 5.4), so it would need its own soundness argument.

6. Follow-up decision: allow the whole diagonal family via EC, unconditionally

After point 4's re-encodings shipped, we revisited whether `[c]` should stay
restricted to the Unqomp-qfree subset (not/cnot/swap) or admit the diagonal
family too. Decided: admit it. The restriction had quietly conflated two
different questions -- "is dropping a value built from this gate sound" and
"does the gate happen to look like a classical function" -- and only the
first is actually the type checker's job. Given (a) Uncompute.hs's reversal
is now full and faithful for any gate at all, and (b) an unrecognised gate
name already fails loudly at uncompute time rather than silently (both true
regardless of this decision), restricting *which* correctly-invertible names
are admissible doesn't buy any additional soundness -- it only rejects
well-typed, faithfully-uncomputable programs for computing something the
type system judges "pointless". That's not Qurts's job: a type system
guarantees an operation is safe, not that the program does anything useful
with it. Concretely, this is why example_grover_original.qurts-core (the
pre-fix ancilla/oracle/phase/drop encoding, restored from git commit
b78d43c with `meas()` added back -- see the repo's own git log) is being
kept in the example suite deliberately, specifically *because* it is
"wrong": it type-checks, uncomputes, and runs, and gives a uniform (not
peaked) distribution, since full reversal correctly cancels its own phase
kickback right along with everything else. That's the type checker doing
exactly its actual job and nothing more.

This does not retract point 4b's finding -- classical-basis tracking is
still sound, still more precise than the old name-based skip, and would
still let a program like example_grover_original.qurts-core's actually
produce the *correct*, peaked distribution instead of merely type-checking.
The two are different fixes at different layers: this point (6) is about
what `[c]` is allowed to name (a type-checker admission question, resolved
now); 4b is about whether a specific already-admitted gate's reversal can be
skipped in a specific drop without breaking something else (a scheduling
question, deliberately deferred). The right place for 4b's fix isn't a
per-gate lookup table at all -- it's wherever a `drop`'s reversal actually
gets planned, which doesn't exist as a separate concept yet in this
implementation: `Uncompute.hs` currently does the simplest possible thing
(reverse a value's *entire* tracked history immediately, in place, the
moment a `drop` is reached), not the paper's own fuller reversible-pebble-
game flexibility (Section 5.1: pebbles can be placed and cleared in whatever
order and at whatever point the wielded strategy chooses, which is exactly
the extra freedom a real fix would need to exploit). Uncompute.hs's own
module header already documents this as the project's biggest known gap
("naive strategy only ... what's missing is the paper's split/merge pebble
game"); a sound, selective diagonal-gate skip is one more reason to want
that done properly, not a justification for hand-rolling a narrower version
of it ahead of time in GateInverse.hs.

7. Follow-up (2026-08-12): author says diagonal gates can always be skipped
   during uncomputation -- re-tested the counterexample directly, it still
   breaks

Talked to Kengo. His answer to Question 2 above: we can always ignore Z and
other diagonal gates during uncomputation -- i.e. reinstate the *unconditional*
name-based skip from point 1 (not the basis-confinement refinement from 4b),
full stop, no extra condition.

Before wiring that back into GateInverse.hs/Uncompute.hs, re-ran the exact
H-then-Z-in-one-qif-branch counterexample from point 1 through the real
pipeline, this time with a live simulation rather than a hand-trace, to check
it against this new claim directly. `examples/example_diagonal_skip_counterexample.qurts-core`:

    fn diagonal_skip_test<||>() -> #top bool {
        let c0 = [0]() ; c0 as #bot qbit ; let c = H(c0) ;   -- control qubit, put in superposition
        newlft alpha ;
        let rc = &alpha c ;
        let result = qif rc {
            let q0 = [0]() ; q0 as #bot qbit ;
            let q1 = H(q0) ; let q2 = Z(q1) ;                 -- H;Z, both bare EU, one branch only
            q2
        } else {
            let q0 = [0]() ; q0
        } ;
        drop result ;                                          -- the drop under test
        drop rc ; endlft alpha ;
        let c2 = H(c) ; let ret = meas(c2) ; ret                -- entanglement witness
    }

This type-checks today, unconditionally, exactly as point 2 above already
established (typ_qif's own retagging accepts the #bot-tagged H;Z branch into
the qif's #alpha, droppable result). The last three lines are a witness for
whether `drop result` actually left `c` disentangled and pure: if it did,
`c` is exactly H|0> again, and measuring `H(c)` is deterministic; if `result`
was left entangled with `c` instead (the invalid-discard failure mode
Definition 2.1 forbids), tracing it out leaves `c` maximally mixed, and
`H(c)` measures ~50/50 regardless of what pure state `c` was "supposed" to
be in -- a clean way to tell "genuinely disentangled" from "just happens to
look right in the Z basis" without having to inspect amplitudes directly.

Results, both from an actual build+`-simulate` run, not hand-traced:

  - Today's code (full/faithful reversal, no skip): 1000/1000 on one outcome.
    Deterministic, as expected -- `c` came back out pure.
  - A scratch rebuild with the unconditional diagonal skip reinstated
    (GateInverse.hs's isDiagonalUnitary/isDiagonalClassical restored exactly
    as point 1 describes them, reverseOrigin's FromGate/FromClassicalGate
    cases skip emitting a step when the gate is diagonal): 510/490. The
    reconstructed reversal applies H (to undo the branch's own H) but skips
    Z, so the "then" branch's ancilla lands on H(Z(H(|0>))) = H((|0>-|1>)/root2)
    = |1>, not |0> -- the two branches of the reconstructed qif disagree
    (|1> vs |0>), which is exactly the entangle-with-the-control failure
    point 1's original hand-traced counterexample described. Reproduced
    end-to-end this time, not just argued.

So, taken completely literally ("we can always ignore Z, unconditionally"),
this reintroduces the exact bug point 1 removed -- the claim and this test
result are in direct tension. Possibilities, none resolved yet:

  (a) The type checker is wrong to accept this program at all -- i.e. the
      guarantee "uncomputed qubits are always qfree" is meant to hold
      *given* a correct type system, and typ_qif's `return (TyBang alpha
      (stripBang t))` (TypeChecker.hs) is the actual bug: it silently
      strips whatever bang-tag a branch produced (including #bot from a
      bare-EU chain like H;Z) and retags the qif's result as droppable
      #alpha, with nothing tracking that the branch's own value was never
      actually confined to a basis ket. If so, the fix belongs in the type
      checker (reject, or require some further condition on, a branch whose
      own history isn't qfree before letting typ_qif retag it droppable),
      not in Uncompute.hs at all.
  (b) The "always ignore diagonal gates" guarantee is meant to hold under
      some narrower condition this test doesn't satisfy -- need to ask what
      that condition actually is, since "gate is named Z/S/T" alone isn't
      it (this test is a direct counterexample to that literal reading).
  (c) Something about the surrounding discipline (how newlft/borrow/qif are
      meant to be used together) rules a program shaped like this out in
      practice, even though nothing in the current implementation actually
      enforces it.

Not implemented pending Kengo's read on this specific reproduction. The
scratch build used for the 510/490 run was not committed -- only the
counterexample program and this writeup are.

8. Resolution (2026-08-12): Kengo confirmed the claim; the gap was (a) --
   typ_qif's own retagging, not the diagonal skip. Fixed by matching Fig. 15
   literally.

Kengo confirmed the diagonal-gate-skip claim holds. That meant possibility
(a) from point 7 was the live one: the type checker was letting through a
program it shouldn't have. Went back to the paper's actual Fig. 15 (rendered
the page directly, not just pdftotext -- extraction was garbled enough on
this figure that it was worth checking by eye) to see exactly what
EXPR QUANTUM IF requires:

    x: &^alpha qbit in Delta      alpha in A      (Gamma,A) |- B_i : T
                                  B_i : PQ              T : PQ
    ------------------------------------------------------------------
    qif x B_|1> else B_|0> . #^alpha T : (Gamma+Delta, A) --> (Delta, A)

B_i : T for *both* i in {|1>,|0>} -- one literal shared T, exactly like
EXPR CLASSICAL IF right next to it in the same figure (same shape: both
branches judged against the identical T). No subtyping anywhere in that
premise. TypeChecker.hs's EIf case (classical if) already enforces this
literally (`unless (t1 == t2) $ throwError (TypeMismatch t1 t2)`) -- EQIf
was the one place that didn't, instead accepting t1/t2 whenever *either*
subtyped the other (via SUBTY SHORTEN, Fig. 13: `b <= a in A` gives
`P^a T <= P^b T`, i.e. a pointer type narrows from a longer lifetime to a
shorter one) and picking whichever "won", then discarding its own tag
entirely and re-wrapping with a fresh alpha with no check that alpha was
even reachable from it. That extra machinery is not in the rule above at
all -- it was this implementation's own invention, not licensed by the
paper, and it's exactly what let point 7's counterexample through: #TOP
qbit ≤ #bot qbit always holds (SUBTY SHORTEN with a=TOP, since everything is
<= TOP), so the bare-[0]() branch (#TOP) and the H;Z branch (#bot, EU's
pin) were accepted as "compatible", #bot "won" the merge (correctly, by
subtyping), and then got silently overwritten with alpha regardless -- the
one-way-door property of #bot was never actually checked against the
target it was being retagged into.

Fix: `checkExpr (EQIf x bt bf)` (TypeChecker.hs) now requires `t1 == t2`
exactly, matching Fig. 15 and mirroring what checkExpr's EIf case already
does. No more subtyping search inside the rule itself. Re-ran the
counterexample: now rejected outright at type-check time --
`TypeMismatch (TyBang LBottom TyQBit) (TyBang LTop TyQBit)` -- not merely
mis-uncomputed at runtime. Renamed to
examples/example_diagonal_skip_counterexample_error.qurts-core to match the
repo's own _error convention.

This tightening is exactly what the paper's own stmt_coercion rule exists
to route around: a qif whose two branches are "morally the same value" but
happen to carry different lifetime tags (typically because one branch
nests a further qif, whose own conclusion is unconditionally re-tagged
#^alpha by the very same rule, while its sibling branch is a bare [0]()
sitting at #TOP) now needs an explicit `x as #T qbit;` inside whichever
branch to unify the two literally, before the outer qif's own rule applies
-- the programmer's job via an explicit statement, not something typ_qif's
own algorithm should paper over silently. This broke 8 examples that relied
on the old auto-merge (example_and, example_grover's oracle/diffusion_phase,
example_grover2's kickback_and/kickback_all_zero,
example_grover_amplified(2)'s clause_or2/clause_nand2/clause_impl/
clause_or2_neg_second/all_satisfied3(6)/non_zero, example_grover_original's
oracle/non_zero, example_reinitialise, example_self_controlled_uncomp) --
all fixed the same way, by inserting the coercion into whichever branch's
type needed narrowing to match its sibling (SUBTY SHORTEN only narrows,
never widens, so the direction matters: #TOP can always narrow into
whatever the sibling is; #bot can only ever be matched by something already
at #bot, never coerced *into* from anything else, and never coerced *out of*
to anything else either -- confirming #bot really is a one-way door end to
end, now enforced at exactly the point that used to leak it). All 43/43
examples still parse+check, 25/30 still uncompute (same five pre-existing
pebble-game gaps as before, no new regressions), and
example_grover/example_grover2/example_grover_original all still simulate
to the same peaked distributions as before (~939-943/1000 on the marked
state) -- confirmed by an actual rebuild+simulate run, not just re-argued.

9. Refinement (2026-08-12): automatic lifetime intersection, replacing the
   manual `as` coercions from point 8 -- confirmed with Kengo

Point 8's fix (`t1 == t2` exactly, no subtyping at all) is what Fig. 15
literally states, but the paper is deliberately strict there to keep its own
proof simple -- Kengo confirmed the *implementation* is expected to be more
permissive, the same way Rust doesn't force two if/else branches to name the
identical lifetime, only to be unifiable: infer the *intersection* (greatest
lower bound) of the two branch lifetimes automatically, rather than making
the programmer spell out an explicit coercion every time. Concretely: if a
lifetime is ⊤ ("static"), the intersection with anything is just the other
lifetime (⊤ is infinite, so it imposes no restriction at all); otherwise,
synthesise something that "ends together with whichever of the two ends
first."

Implementation: rather than literally minting a fresh `newlft`-tracked
variable for that "something" (which would need new bookkeeping to cascade
an `endlft` of either parent into ending the derived one too -- easy to get
out of sync), added `LMeet LifetimeAtom LifetimeAtom` as a purely structural,
derived lifetime term (Ast.hs) that is *never* registered in
LifetimePreorder's own ltVars at all. `isActive`/`leq` (TypeChecker.hs)
handle it recursively instead: `isActive (LMeet a b) = isActive a &&
isActive b` -- computed fresh every query, so it automatically stops being
active the instant either parent does, for free, with nothing to keep in
sync. `meetLft` computes the actual meet (⊤ is the identity, ⊥ is absorbing,
otherwise builds an `LMeet` node); `unifyBranchTypes` walks two branch types
structurally, meeting the lifetime at each corresponding `#^𝔞`-position
while still requiring an exact match everywhere else (different type
shapes -- bool vs qbit, say -- are still a hard TypeMismatch); `retagQifResult`
replaces the old "discard the branch's own tag, substitute a fresh α" step
with "meet α *into* the branch's own tag" -- never information-destroying,
unlike the original unsound version this whole investigation started from.

Re-verified by literally reverting all 8 of point 8's manual `as`
coercions back to their original (pre-session) form and re-running the
suite: 6 of the 8 (example_and, example_grover_amplified(2),
example_grover_original, example_reinitialise, example_self_controlled_uncomp)
now pass with *zero* manual coercions at all -- the automatic meet handles
the #top-vs-#specific-lifetime merges natively (meet(⊤,α)=α, recovering
exactly the old "just use α" behaviour, but only when it's actually sound
to do so). The remaining 2 (example_grover's oracle/diffusion_phase,
example_grover2's kickback_and/kickback_all_zero) failed differently:
ReturnTypeMismatch, not TypeMismatch -- because these mix a #bot-tagged
branch with the qif's own control lifetime, and meet(bot, anything) = bot
is genuinely the most precise type derivable (not an artifact to work
around), which no longer matches what these functions had *declared*
(`-> #alpha qbit`, inherited from when the old unsound retag always
produced α regardless). Fixed by changing their declared return types to
`-> #bot qbit` (removing the now-redundant `z as #bot qbit;` casts their
own callers had already been inserting immediately after every call site,
confirming #bot really was what those call sites needed all along).

Ran the H;Z-in-qif-branch counterexample once more under this refined
version: the qif itself *now type-checks* (meet(⊥,⊤)=⊥ is accepted, unlike
point 8's stricter version), but the subsequent `drop result;` fails with
`CannotDrop (TyBang LBottom TyQBit)` instead of point 8's `TypeMismatch` --
`canDrop`'s own `drop_own` rule (`isActive a`) already made `#bot` provably
never droppable (`isActive LBottom = False`), completely independently of
this qif change. This is a *better* rejection than point 8's, not just a
different one: it correctly accepts a qif that mixes #bot/#top branches for
any purpose *other* than immediately dropping the result (e.g.
example_grover's oracle, which threads its #bot-derived z onward to be
measured, never dropped) instead of blanket-rejecting the merge itself, and
only refuses at the exact point where droppability is actually claimed.
Updated the counterexample's own `.expected` file (`CannotDrop`) to match.

Full suite after this refinement: 43/43 parse+check (same as before this
whole investigation started), 25/30 uncompute (same five pre-existing
pebble-game gaps, no new regressions), and example_grover/example_grover2/
example_grover_original all re-simulate to the same peaked distributions
(~931-954/1000) -- confirmed by an actual rebuild+simulate run.
