Notes for the meeting with Kengo
================================================================================
Purpose: figure out whether continuing this (a from-scratch qurts-core
implementation in Haskell: parser, type checker, automatic uncomputation,
circuit compiler) is worth it -- i.e. whether the four open questions
below are genuinely open, genuinely hard, and genuinely relevant to where the
paper/project wants to go next.

--------------------------------------------------------------------------------
PART 1: What actually exists right now (pipeline overview)
--------------------------------------------------------------------------------

    .qurts-core source
    [1] Parse        (bnfc/ -- Alex/Happy generated lexer+parser from a BNFC
          |           grammar file, converted into our own Ast.hs shape by
                      AbsQurtsToAst.hs)

    [2] Type check    (typeChecker/TypeChecker.hs)
    [3] Uncompute     (uncompute/Uncompute.hs, GateInverse.hs)
    [4] Circuit IR    (circuit/Circuit.hs)
    [5] Qiskit render (circuit/build_circuit.py -- draws the circuit, and,
                        with --simulate, runs it on Aer and prints outcome
                        counts)

Status of each stage:

[1] Parse -- complete. Full core grammar (Fig. 3), nothing missing (at least
I didnt have any issues with it so far).

[2] Type check -- audited rule-by-rule against every typing judgement in the
    paper (Figs. 5-8, 13-17) across several passes,
    which turned up and fixed several implementation bugs along the way
    (unenforced lifetime well-formedness assumptions from Section 3.2.1, a
    couple of soundness gaps around variable reuse and lifetime-relation
    bookkeeping, an arity-checking gap in [c](x)). The four genuinely open questions,
    where it's *not* clear whether the paper's own formal rule or the
    implementation should give way, are below.
    Fig. 13's full subtyping lattice (shorten, reborrow, double-affine,
    borrow-affine, affine-borrow, tuple, unit) is implemented and exercised
    by the examples. 
    (automatic lifetime/copy/drop inference, mutable references, for-loops --
    Section 3.1's examples use these) is also explicitly out of scope: we
    target qurts-core, not full Qurts.

[3] Uncompute -- the real gap of the prototype, and the most interesting stage. 
    Rewrites each `drop x` into the literal reversed sequence of whatever produced `x`,
    in place, immediately, right where the source wrote `drop` -- NOT the
    paper's own flexible pebble-game placement (Section 5.1), which allows
    computing/uncomputing in whatever order and at whatever point a chosen
    strategy picks. This "naive strategy only" gap is what's actually 
    blocking further progress, see Part 2, question 2.

    Handled: EU/EC gate chains on a single tracked value back to init,
    bare renames/borrows/copy/measured-bool, pair-destructure of a literal
    pair, qif where each branch is self-contained, function calls (inlined,
    recursive composition confirmed two levels deep).

    Not handled (5 of 28 non-error examples, all needing the same missing
    machinery): a `drop` nested inside a qif branch; a qif branch (or
    callee) whose result depends on a reference created *locally* inside
    that branch (typ_qif ties the reconstructed result's lifetime to the
    control's own, so there's no way to reverse it early without the
    paper's split/merge pebble game); one half of a jointly-computed pair
    while its sibling is still live.

[4] Circuit compilation -- essentially complete for everything stage [3]
    can produce. qif compiles to genuinely multi-controlled (Toffoli-shaped)
    gates; function calls inline; classical `if` on a compile-time-known
    bool picks a branch statically with zero gates; classical `if` on a
    *measured* bool compiles to a real Qiskit if_test control-flow block.

[5] Render/simulate -- works, spot-verified against known-correct
    distributions (Bell state, Toffoli truth table, Grover, a classical
    if_test example where the measured condition and its corrected qubit
    always agree). Not yet fully complete - but I think all examples work.

Net: a working parse-check-uncompute-circuit-simulate pipeline exists
and runs end to end on everything the paper's core calculus covers, except
for the split/merge pebble game.

---------------
Open questions
---------------
First two came out of trying to implement Grover's algorithm (the paper's own
running example, Section 3.1 / Appendix A) faithfully in qurts-core. Full
technical writeup with worked examples and verified counterexamples is in
grover.txt at the repo root; this is the short version.

--- Question 1: is Section 3.1's phase(pi) idiom part of the formal core,
    or deliberately out of scope?

Section 3.1's own Grover sugar desugars to:

    let r = &xl;
    let tmp: #qbit = oracle(r);
    qif &tmp { phase(pi) } else { noop };
    drop tmp;

This is not expressible in qurts-core as formalised in Section 3.2, and we
checked this directly rather than assuming it:

  - phase(pi) is "the map -1: C -> C" (Appendix A) -- it produces no qubit,
    so a qif branch built from it has type (). typ_qif requires both
    branches Purely Quantum (Fig. 7); () fails that unconditionally.
    Confirmed: type-checking a qif with a ()-typed branch fails with
    NotPurelyQuantum in this prototype.
  - The qif line above is used as a bare statement, result unnamed. The
    core grammar's Stmt has no "expression as its own statement" form --
    every expression must be let-bound.


question worth asking directly: is there a *planned* way to formalise this
specific idiom (a targetless global-phase primitive, usable only inside a
qif, exempt from the Purely Quantum restriction, compiling directly to a Z
gate on the qif's own control), or is the expectation that qurts-core
programmers always encode phase kickback some other way (a real ancilla,
or -- our workaround -- applying the phase directly to one of the qubits
already in play)? If there's no planned answer yet, this seems like a
genuinely small but concrete language-design gap: core-calculus qurts-core
currently cannot express this example's cleanest formulation.

--- Question 2: does automatic uncomputation need the type system to know
    about basis states, or is that fundamentally a scheduling question?

From my limited understanding of quantum physics, it is wrong to uncompute
"diagonal phase-only gates" as long as they are applied to a basis state.
Is that correct? Do we fix that by drop-placement in the code? or does the
automatic uncomputation have to check that (by... tracking basis states all
over the program?)

 Consequence: the papers Grover example's own oracle (a
temporary boolean ancilla, phased via a rebind, then dropped) isnt
working -- undoes its own phase kickback
right along with everything else, giving a uniform instead of peaked
distribution. Unqomp's own qfree criterion (which
Qurts's uncomputation approach is modelled on) already excludes Z for the
same reason, and Unqomp's paper says outright that Grover/Deutsch-Jozsa's
phase kickback is "built by hand, entirely outside" their automatic
machinery.

I worked around this two ways in the examples (a direct phase oracle with
no ancilla at all; a real |-> phase-kickback ancilla disposed of via measure
rather than drop, since it's a genuinely different physical operation that
doesn't try to unitarily undo the kickback). Both work, verified by
simulation.

But there's a real unresolved question underneath the workarounds: is there
a *principled*, type-derivable way to decide, per drop, whether a given
gate's reversal is safe to skip without destroying an intended effect
elsewhere (e.g. by tracking whether a value is provably confined to a
computational basis ket -- we sketched this, it's sound, but it's a new
analysis the paper's own type judgements don't carry: Fig. 4's typing
context only ever holds a type and an aliveness, nothing about quantum
state)? Or is "when to uncompute, and whether a given step even needs
reversing" fundamentally not a *type* question at all, but a *scheduling*
question that belongs entirely in the pebble-game semantics (Section 5),
where a strategy is free to choose not to place/clear a pebble in a way
that would destroy a needed correlation? 

--- Question 3: does typ_qif really require the *same* type from both
    branches?

Found during a full correctness pass over the implementation against the
paper (checking every rule in Figs 5-17 against what the code actually
does, not just the two issues above). Both the simplified rule (Sec 3.2.2's
prose) and the fully-formal one (Fig 15, "expr quantum if") state each
branch's own judgement as "(Γ, A) ⊢ B_i : T" -- literally the *same* T for
i=0 and i=1, no subtyping slack anywhere in either version.

I had to relax this to get the paper's own Grover example to type-check.
Concretely, example_grover_original.qurts-core's `oracle` (the paper's own
boolean-oracle-then-phase-kickback shape) has an outer qif whose two
branches are:

  then (controlled by x): a further nested qif (controlled by y), whose own
    two branches are both [1]()/[0]() (#top qbit each) -- so, per typ_qif's
    own retagging, this nested qif's *result* comes out #alpha qbit (alpha
    being x and y's shared borrow lifetime here);
  else: a bare [0](), giving #top qbit directly -- nothing nested inside
    this branch for typ_qif's retagging to apply to at all.

So the outer qif's own two branches are #alpha qbit vs #top qbit --
different types, related only by subtyping (#top qbit <= #alpha qbit, since
alpha <= top always holds). Requiring literal equality, as both versions of
typ_qif state, rejects this outright; the implementation instead accepts
two branches whenever one subtypes the other, and takes the wider type --
and that relaxation is exactly what lets `oracle` (and so the whole Grover
example) type-check at all, not an unused generalisation.

Is this a real gap in the formal system -- i.e. should typ_qif read "up to
subtyping", the same way stmt_coercion is what makes subtyping usable
anywhere else in the calculus, and Fig 15's own rule is under-specified? Or
is there a different, paper-intended way to write `oracle` that never
produces mismatched branch types in the first place, making our relaxation
a convenience that happens to also accept programs the core calculus never
meant to?

--- Question 4: does stmt_borrow's own "α ∉ A_ex,Π,f" premise actually hold
    up against a function that needs to hand a *locally built* value into a
    further call under its own return lifetime?

Found in the same audit pass, while implementing Question 2/3's fix as an
actual type-checker change (not just an observation): Fig. 16's
stmt_borrow requires the SAME premise as stmt_end_lifetime -- a function
may only borrow with a lifetime it introduced itself, never one of its own
external generic parameters. Enforcing this literally breaks
example_grover_amplified.qurts-core's `oracle<alpha>`, which does:

    let c1 = clause_or2<alpha>(x1, y1);   -- c1: #alpha qbit, built locally
    let rc1 = &alpha c1;                   -- borrow it with oracle's OWN alpha
    let result = all_satisfied3<alpha>(rc1, rc2, rc3);  -- -> #alpha qbit
    result                                  -- matches oracle's own -> #alpha qbit

(to be fair, its fine if this breaks - I wrote it myself)

Borrowing with a *fresh* local lifetime instead doesn't work around this:
newlft's own rule ties any new local lifetime to be shorter than every
already-active one (so a fresh beta would end up beta ≤ alpha), and a
#beta qbit result can never be coerced back up to #alpha qbit afterward
(subty_shorten only narrows). So using oracle's own external alpha for
this borrow looks structurally necessary, not a convenience -- any
function that computes something locally and needs to feed it into a
further call while returning a result tagged with its *own* lifetime seems
to need exactly this pattern. (We ended up enforcing stmt_end_lifetime's
copy of this same premise -- a function still may not *end* an external
lifetime, which no example needs to and which desyncs the caller's own
bookkeeping if allowed -- just not stmt_borrow's copy.)

Same shape of question as Question 3: is Fig. 16's stmt_borrow rule
over-strict relative to what the paper's own multi-function examples
actually require, or is `oracle` written in a way the calculus never
intended and there's a different, correct way to structure it that we're
missing?

--- Aside: pq_expr (Fig. 7) doesn't literally say what its own prose means

Fig. 7's own pq_expr rule is "𝑒 : PQ" whenever
"𝑒 ≠ meas 𝑥 ∧ ((𝑒 = 𝑓⟨𝛼⟩(𝑥) ∧ fn-name(𝐹) = 𝑓) ⇒ 𝐹 : PQ)" -- i.e. it only
ever inspects the *top level* of 𝑒: is it literally a bare `meas x`, or a
call to a non-PQ function. It says nothing about classical `if`. Read
completely literally, `if x { let m = meas(p); m } else { ... }` would
satisfy this formula outright (it's neither of the two excluded shapes),
even though the surrounding prose ("this rule only applies when no
measurement occurs under quantum control... does not include any
measurement") clearly intends this to hold transitively, not just at the
expression's own top level -- the whole point of Purely Quantum is to keep
a measurement from ever hiding inside a qif branch, by any route.

My checkExpr's isPurelyQuantumExpr hard-excludes *any* classical `if`
used inside a qif branch outright, rather than trying to recurse into its
own two sub-blocks the way the prose implies it should. That closes the
gap conservatively: it can reject a classical `if` that happens to contain
no measurement at all (stricter than necessary), but it can never let one
hiding a measurement slip through (which is the only direction that would
actually be unsound). Nothing to fix -- just flagging that the formula in
Fig. 7 doesn't, on its own, literally forbid what its own prose says it
should.
